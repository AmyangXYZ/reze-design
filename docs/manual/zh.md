# Reze Design 使用手册

[English](https://github.com/AmyangXYZ/reze-design/blob/main/docs/manual/en.md) · **简体中文**

Reze Design 是一个 MMD 场景的设计、渲染与分享平台，运行在浏览器中：读取 MMD 社区十余
年积累的模型与动作，以 WebGPU 渲染，最终输出为一个视频文件，或一个任何人都能打开并自
由转动视角的实时页面。

它由自研引擎驱动——reze-engine，一个为本平台构建的 WebGPU 渲染器——平台的能力边界正
来自于此：材质是直接编译为 WGSL 的节点图，背景特效是对着实时场景即写即用的着色器，视
频导出以离线方式逐帧推进时钟，任何机器上渲染 4K 60 帧都能得到逐像素一致的结果。围绕引
擎的是一个跨会话保留工作的现代编辑器，以及一个平台：每个发布的场景都是一个可打开、可
转动、可二创的实时页面。

手册的顺序就是你工作的顺序：**第 0 节**是背景，写给没有接触过 MMD 的读者。**第 1 节**
把完整流程走一遍——导入素材、取景、打光、定风格、导出、发布。**第 2 节**深入三个创作
面——调色预设、WGSL 背景特效、节点材质图——每一节都给出完整契约，读完即可独立创作。
模型、动作与音乐的来源见[附录 B](#附录-b-去哪里找模型动作和音乐)。

# 0. 关于 MMD

MikuMikuDance（**MMD**）是樋口優开发的免费 3D 动画软件，2008 年 2 月发布，最初用于让
初音未来跳舞。真正生长起来的，是围绕它形成的**可自由拼装的生态**：模型是一个人做的一
个文件，舞蹈是另一个人做的另一个文件，运镜是第三个文件；它们之所以能拼在一起，只是因
为所有人都遵守同一套骨骼命名。一支成品 MMD 视频，背后常常是五到十五位素未谋面的作者。
借物表之所以成为社区文化，2011 年的动作文件之所以今天仍然可用，根源都在于此。软件本身
则是一个 32 位、基于 DirectX 9 的 Windows 程序，开发在 2010 年代后期停止，手机与平板
更无从谈起。需要现代渲染的人只能转向 Blender 或 Unity：画面确实出色，但可拼装性在导入
这一步就中断了——转换过的资产、手工重建的材质，别人已无法直接取用。

MMD 带动的这套画风，如今早已进入主流。原神、深空之眼、鸣潮走的都是**三渲二**——把 3D
角色渲染出手绘动画的观感——每一部背后都有一个庞大的同人圈，二次创作产量惊人，其中相当
一部分至今仍由 MMD 的模型与动作完成。让这套画风真正能在浏览器中运行的是 WebGPU；而在
浏览器这条路上，早已有人做过扎实的工作：
**[babylon-mmd](https://github.com/noname0310/babylon-mmd)** 把 PMX 模型、VMD 动作、
物理和 MMD 兼容着色带进了 Babylon.js，至今仍是网页端 MMD 能做到什么程度的参照。
**[reze-engine](https://github.com/AmyangXYZ/reze-engine)** 选择了另一条路：不架设在
通用引擎之上，而是为 MMD 专门编写一个渲染器。引擎之上有两个应用：**Reze Design**，即
本手册所讲的这个，负责场景的设计、渲染与发布；以及
**[Reze Studio](https://github.com/AmyangXYZ/reze-studio)**，本项目时间轴的来处、独立
的动画编辑器。两者只需一台装有现代浏览器的机器即可运行，直接读取生态中现
成的文件，并把一个场景变成一条链接——他人打开即可转动视角，也可以继续做下去。

# 1. 做一个场景

## 1.1 整体流程

一个场景通常是一次做完的。顺序不必严格，关键在于每一步都可回退：所有设置始终保持可
调，导出之前不会固化任何东西。

> 载入模型 → 给它动作 → 加音乐 → 定镜头 → 打光 → 选风格 → 导出视频，或发布场景。

本节即按这条主线展开。一望即知的控件——选择文件、点击色块、按下播放——不再赘述，
[附录 A](#附录-a-控件速查) 列出了每个控件及其取值范围。

浏览器需要支持 WebGPU：Chrome / Edge 113 以上，或 Safari 26 以上。编辑器提示无法启动
时，基本都是这个原因。整个过程不上传任何文件，它们只留在当前标签页中，直到你主动
发布。

## 1.2 模型、动作、音乐

打开 **Assets** 载入模型：既可以选择包含 `.pmx` 的整个文件夹，也可以直接选择下载得到
的 `.zip`，两者都支持拖放。


| 格式     | 是什么                                                                                     |
| ------ | --------------------------------------------------------------------------------------- |
| `.pmx` | 模型：网格、材质、贴图、骨骼、物理                                                                       |
| `.pmd` | 早期模型格式，请先用 PMX Editor 转换为 PMX                                                           |
| `.vmd` | 关键帧。同一个扩展名既可能是**身体动作**，也可能是**镜头动作**，它们载入到不同的槽位                                          |
| `.fx`  | MikuMikuEffect 的 DirectX 9 特效。这里对应的是[场景特效](#23-用-wgsl-写场景特效)和[着色图](#24-材质着色图)，用 WGSL 编写 |


**保持模型文件夹完整。** PMX 按相对路径引用贴图，若只把 `.pmx` 单独取出载入，模型会呈
现为白色或灰色。这是初次使用时最常见的问题。

将身体动作载入同一个槽位，播放条随即出现，按下播放即可。再添加一个模型，它会拥有自己
的槽位与动作，而镜头、灯光与风格则全场共用一套。音乐绑定在时间轴上，拖动进度或开启循
环，声音都会随之同步。动作按标准骨骼编写，因而可驱动任何模型——体型差异较大时会出现脚
下打滑或悬空，换用身材更接近原作者所用模型的角色即可解决。

头发与裙摆采用物理模拟，跳转之后需要若干帧才能稳定。这段抖动不会进入导出文件：导出器
会先渲染一段预热，再开始录制。

## 1.3 镜头

左键拖动旋转，右键拖动平移，滚轮缩放。

公开发布的舞蹈动作大多还附有一份**镜头动作**——另一个 `.vmd`，其中是编舞者自己的运镜。
载入 **Assets → Camera** 后，画面即完全按作者的设计走，此时鼠标不再起作用；播放条上的
开关可随时把控制权交还给你，播放不会中断。

需要手动构图时，**Scene → Camera** 比鼠标精确得多。最常调整的是 Target Y：角色身高约
为 10 个单位，因此目标高度取 10 左右为脸部特写，取 5 左右为半身，取 0 则是贴地仰拍。任
何滑杆的数值都可以精确输入——双击数字即可。

**跟踪中心**把镜头轨道绑定到角色的中心骨骼上：动作在舞台上大范围移动时，画面始终跟着角
色走，而不会把人跳出画外；此时目标滑杆的含义变为相对角色的偏移，而非世界中的固定点。已
载入并开启的镜头动作仍然优先。

## 1.4 灯光

灯光由三部分构成，真正需要斟酌的地方不多。

**Sun** 是主光。阴影贴图与它方向一致，因此明暗与投影始终吻合。最见效果的是
**Elevation**：压低时投影拉长、轮廓分离明显；抬高时人物变平、投影几乎消失。

**World** 是环境补光，负责太阳照不到的部分。强度为 0 时背光面全黑，过高则画面发平。多
数风格采用冷调环境配暖调主光，或反之——主光与补光之间的**色彩反差**，比任何一方的强度
都更起作用。

**Bloom** 是高光溢出。强度为 0 即关闭，此时整个 pass 会被跳过。阈值接近 1.0 时只有真正
的高光才发光；压到 0.3 左右，整幅画面都会起雾，这是一种相当重的取向，需要有意识地
使用。

**Ground** 有一点值得单独说明：不透明度只淡化地面，阴影仍然保留。将不透明度归 0 而保持
阴影开启，即可得到一块「影子接收板」——影子浮在背景上，不会有地面平面与照片背景相互
干扰。

## 1.5 角色背后的层

从后往前共四层。最底层是**背景色**；其上是 **backdrop**（平铺在场景之后的一张图）或
**skybox**（2:1 等距柱状全景，投影成无限远的天穹，随镜头转动，转动视角如同望向真实环
境）；最上层是**场景特效**——一段可以画在角色前后两侧的着色器。星空与极光画在身后；雨、
落樱、火星与雾画在身前，而且身前那一层知道角色有多远，所以从肩后掠过的雨滴会被挡住。

在 **Scene → Background** 中选择其一，或打开库查看全部。自行编写的方法见
[§2.3](#23-用-wgsl-写场景特效)。

## 1.6 舞台

backdrop 是角色身后的一张图；**舞台**则是角色置身其中的几何体——神社、街道、演出场
地——和模型一样以 PMX 分发，从 **Assets → Stage** 载入，文件夹或压缩包均可。

一个场景只保留一个舞台，再上传一个会替换掉原有的。其下有：

**摆放。**位置、旋转与统一缩放。舞台 PMX 的朝向取决于作者当时的工作方向，尺度更是相差
悬殊，因此通常需要先转一转、缩放一下才对位。重置会让整块回到默认值。

**开关。**舞台作者习惯把可选项做成变形（morph）——屋顶的有无、招牌的替换、霓虹配色的
切换。没有任何动作数据驱动它们，你设定的权重就是场景的一部分，会随文档一起保存。列表只
显示渲染器真正能驱动的变形，所以这里的每一个滑杆都有实际效果。

**地面会关闭。**舞台自带地板，而内置地面平面处在同一高度，两者同时绘制会逐像素争夺深度。
载入舞台后 Ground 一节变为不可用并给出说明；其设置会被保留，移除舞台后自动恢复。

背景特效在舞台之后照常运行——落樱或星空掠过神社的方式，与掠过 backdrop 时一致。

舞台的材质就是普通材质：它们出现在 Materials 标签中，和角色一样可以使用样式组与着色器
图。但它们**不会**被自动分组——自动分组依据的是头发、皮肤一类的名称，用在建筑上毫无意
义，偶尔还会以打乱整个场景绘制顺序的方式出错。新载入的舞台使用中性的默认图，需要更进一
步时再手动分组。

许多舞台把灯光**烘焙进了贴图**。那些阴影是图像的一部分，不会随太阳方向改变，也不会与角
色投下的实时阴影相匹配。这是舞台本身的性质，不是某个设置。

## 1.7 风格

**改变全局最快的一步：按 ⌘K，输入渲染风格。**两套内置风格——*深空之眼* 与 *鸣潮*——
各自是一整套观感，选中其一会按角色逐组替换：身体组换成那套的身体观感，头发组换成它的
头发观感。那套风格没有对应角色的组会原样保留，因此舞台材质、你自己搭的图、以及中性
默认图都能安然度过一次切换。

有两项场景设置会跟着一起走，因为它们本就属于这套观感、而不只是摆在旁边：**视图变换**
（鸣潮是在 Standard 下调的，深空之眼是 Filmic，互换着看就是另一张画面），以及**世界光**
——每个表面都会把环境光乘进去，为一套调好的世界色会和另一套打架。太阳不动：主光放在
哪里属于布光，切换风格没有理由去挪它。

这个选择会被记住，因此你下一次载入模型时，它会直接以同一套风格出现，而不是自动分组时
的那一套。**恢复默认场景**会把它清回深空之眼——演示场景的角色与世界光本就是那一套，
记着另一套只会让下一个模型和眼前的角色对不上。**新建场景**则不动它：空舞台上没有角色
可以对不上，你正在用的风格自然带着走。

决定画面观感的有两套机制，作用的尺度不同。

**调色预设**处理的是整幅成品画面，位于灯光之后、导出之前。「渲染出来了」与「看着对
了」之间的差别就在这里：同一个场景，调暖调亮是夏日午后，调冷并压暗暗部则成了夜晚。
**Scene → Grade** 中提供了几套内置预设——*Neutral*、*Bloody*、*Cyberpunk*、*Divine*、
*Moonlit*、*Sakura*——强度滑杆**按预设分别记忆**，来回试过几种再切回来，仍是你上次为它
设定的强度。自行制作的方法见 [§2.2](#22-调色预设)。

**样式组**决定表面如何响应光照。这套概念在 MMD 中没有对应物：

> **样式组**是一组共用同一种外观的材质，**着色图**是定义这种外观的程序。每个样式组恰
> 好使用一张着色图。

一个 PMX 模型少则十几个材质，多则六十余个：脸一个、头发一个、衣服若干。逐个设置并不现
实，因此载入时会按名称与属性自动归组——头发归入头发组，眼睛归入眼睛组，皮肤归入身体
组。遇到结构特殊的模型难免归错，**Materials** 标签即是修正之处：将材质拖到别的组、新
建一组、隐藏多余的挂件，或为某一组更换着色图。

有两处行为需要留意。其一，当某组的着色图与其来源的库条目不一致时，会标记为
**edited**；这份差异随场景一同保存，因此发布出去的场景能原样重现你的成果。其二，部分
组带有**角色（role）**，影响的不只是着色——头发与眼睛走专门的 pass，丝袜需要 alpha
hashing 才能在多层叠加时正确排序。角色由系统推断，头发组与布料组表现不同即源于此。

逐个节点搭建着色图的方法见 [§2.4](#24-材质着色图)。

## 1.8 编辑动作

载入的动作不是定死的。播放条下面的时间轴打开的就是当前正在播放的东西的关键帧，
改动会作为 VMD 写回场景。

看的是什么，由三个选择决定：

| | |
| --- | --- |
| **哪条轨道** | 动作、表情或镜头那一行上的编辑按钮 |
| **哪个通道** | 标签栏——旋转、位移、权重，或镜头的某个通道 |
| **哪根骨骼** | 左边的列表，或者在视图里双击角色 |

**摆姿势。** 拖动选中骨骼上的操纵器，姿势就写到播放头所在的那一帧，那里没有关键帧
就新建一个。属性面板里的滑块做的是同一件事，只是用数值；你拖哪个通道，时间轴就跟到
哪个通道。

**时间。** 在关键帧条上拖动一个关键帧就是把它在时间上挪位置。曲线那一半画的是同一
批关键帧的数值，所以一个关键帧可以同时改时间和改数值。

**缓动。** 两个关键帧之间的贝塞尔就是 VMD 自己的那一条——和 MMD 写进文件的是同样的
四个字节——显示成一个 127×127 的方框和两个控制点。拖它们，或者取八个预设之一。曲线
属于某一个关键帧，所以只有选中了关键帧、或者播放头正好停在关键帧上时，编辑器才是可
用的。

**轨道操作。** Insert 和 Delete 作用在播放头处。**Simplify** 对稠密的轨道拟合曲线，
丢掉不需要的关键帧——这正是让一段捕捉或重定向来的动作变得可以手工编辑的关键。
**Clear** 清空整条轨道。

⌘Z 和 ⇧⌘Z 撤销与重做，按片段独立。所有改动都作为标准 VMD 写回场景自己的槽位，因此
一次编辑能挺过刷新、会跟着发布一起走，也能从它所属的那一行下载下来。

## 1.9 导出

**Render** 标签用于设定画幅与画质，从 2.39:1 宽银幕到竖屏 9:16，最高 4K；也可以只导出
一段，例如 `0:12` 到 `0:30`。该标签打开时，视口会叠加一层取景预览：框住的即是将要录制
的内容。

**Render video** 输出 60 fps 的 H.264 MP4。Chromium 桌面端会先让你选择保存位置，随后
边编码边写入文件，因此再长的 4K 导出也无需整个载入内存。

导出器有两点值得了解。其一，它采用**离线**逐帧渲染，导出质量与显示器无关，也与标签页
是否位于前台无关——机器较慢时产出的文件完全相同，只是耗时更长。其二，录制的就是你眼前
的镜头、灯光与调色，不存在第二套需要另行同步的渲染设置。

**Capture PNG** 按同样的画幅与分辨率写出单帧，水印与绿幕设置同样生效。它抓取的是屏幕
上当前这一帧的姿势，不跳转也不重置，没有动作亦可使用——发布场景所需的封面图即由它产
出。封面建议使用 1080p 抓取：细节较多的场景在 4K 下容易超过 20 MB 上限。

**Green screen** 把背景换成纯 `#00FF00`，方便在别处合成，也就是 MMD PV 的经典流程。

**导出场景本身**的入口在场景菜单：点击左侧栏顶部的图标（面板收起时，点击悬浮标题条上的
图标）。**导出场景**会生成一个 zip，其中包含场景文档与全部已上传的素材——模型、动作、音
乐、背景图；**导入场景**在任何机器上打开这个 zip，场景即完整还原。同一菜单中还有**新建
场景**（从一个空白的中性布光舞台开始）与**恢复默认场景**（回到内置演示场景）。

**你的工作始终在。**每一次修改都会即时保存：设置与材质记录在 localStorage，上传的模
型、动作与音乐存入 IndexedDB——全部在你自己的浏览器里，发布之前不会有任何内容上传到服
务器。编辑到一半刷新、关掉标签页、第二天再打开，编辑器都会原样恢复到你离开的那一刻，上
传的素材也一并还原。只有四种操作会改变打开时加载的内容：新建场景、恢复默认、导入场景文
件，以及在编辑器中打开他人的场景。

## 1.10 发布

发布会把你的场景变成一个任何人都能打开的页面：一份可自由转动视角的实时渲染。

按下 **Share** 之前，先确认你是否有权分享。几乎每个模型的下载包中都附有一份**利用規
約**，其中**「再配布禁止」——禁止二次分发——非常常见**。发布需要将你载入的模型、动作与
音频打包上传，场景才能在他人的浏览器中渲染，而这在多数条款下即属于二次分发。导出视频
则是另一回事：视频中并不包含模型文件。条款通常还会涉及改造、R-18 表现、政治宗教用途
与商用。

条款之外还有社区自身的规矩——**借物表**：将用到的每一个模型、动作、特效、曲目连同作者
一并列出，观众循此即可找到原作者。Reze Design 要求必填：

```
模型：Tda式初音ミク・アペンド by Tda / 改造 by …
动作：… by …
镜头：… by …
音乐：… by …
```

借物表之外，对话框还需要名称、简介、最多五个标签与一张封面图。进度按阶段汇报——打包、
上传、发布——失败时会指明卡在哪一步及具体原因。填写的文字随输入保存，因此中途去截取封
面图，返回时简介仍在。

最终得到一条 `reze.design/<你的名字>/<id>` 的永久链接。真正用于解析的是那个短 id，因
此之后修改场景名称、甚至修改你自己的名字，已经分享出去的链接都不会失效。

## 1.11 画廊

**场景画廊**位于左上角标志背后的菜单中，⌘K 里同样可以找到，打开的是所有人发布过的场
景。它的侧栏与其他库完全一致：**全部**、**我的**、**已赞**，各自带有数量，标签则在当
前这一栏里进一步筛选。场景发布成功后，也会在链接旁边给出同一个入口；从账户面板点开自
己的场景数，则直接落在**我的**这一栏。

在某个场景的页面上可以转动视角、播放、点赞。**Open in editor** 会把整个场景搬进你的编
辑器，成为**你自己的一份副本**：模型、动作、灯光、调色与材质分配一应俱全，可直接继续
制作。副本直接复用该页面已经下载好的素材，不会重复下载；在副本准备好之前，你自己的场
景不会被动到。副本是独立的：它以原名加上 `- 复刻` 打开，发布它只会新建一个场景，原作
不受影响。借物表也会一并带过来，请在此基础上继续补充。

账号的意义在于让你拥有自己发布的内容。首次登录时需要**为自己设定名字**，它会出现在你
创建的每一条场景链接中，且**只能设定一次**——正因不可更改，分享出去的链接才能长期
有效。

## 1.12 出问题时

**模型呈现为白色、灰色或黑色。** 贴图未找到，几乎都是因为只载入了 `.pmx` 本身。请载入
整个文件夹，或原始的 `.zip`。

**模型无法载入。** 先确认是否为 `.pmd`——旧模型需用 PMX Editor 转换为 `.pmx`。

**动作在播放，模型却不动。** 动作载入到了其他模型的槽位；也可能是该模型的骨骼命名不符
合标准约定——从其他游戏转换而来的模型常有此问题。

**脚下打滑，或陷入地面。** 模型比例与动作原作者所用模型不一致。

**镜头无响应。** 有镜头动作正在驱动它，在播放条上切回自由视角即可。

**导出较慢。** 它在离线逐帧渲染：一段三分钟的 4K 即为数千张全画质图像。迭代阶段用
1080p 导出一小段，定稿后再进行一次 4K 输出。

**发布失败。** 报错会指明卡在哪一步：*打包*多为缺少某个资源；*上传*多为包体超过 200
MB 或网络中断；*发布*多为登录过期或名称冲突。

# 2. 做出自己的风格

第 1 节讲的是从现成内容里选，这一节讲自己创作——这也是本平台在其他 MMD 工具中没有对
应物的部分：场景的风格在这里是可编程的、实时的，分布在同一条管线的三个层级。**调色**
（§2.2）塑造整帧的色彩；**场景特效**（§2.3）是画在角色前后两层的 WGSL 函数；
**材质图**（§2.4）用节点定义每种表面如何响应光照，编译为 WGSL。每一节都给出完整契
约——读完一节即可在编辑器中创作，也可以直接手写文档。§2.5 说明三者共用的草稿、发布
与版本机制。

## 2.1 渲染管线

先弄清所写的东西究竟作用在哪一层，后面的大半内容便顺理成章。从镜头向内看，由后
到前：

```
  背景色  →  backdrop / skybox  →  fn background (§2.3)
                                        ↓
                                  角色，由样式组各自的
                                  材质着色图 (§2.4) 着色
                                        ↓
                                      bloom
                                        ↓
                                  调色预设 (§2.2)
                                  作用于整幅画面
                                        ↓
                                  屏幕、视频、PNG
```

由此可得：

- **场景特效**是一个文件，可以画在这条链路的两个位置上；用哪一个，由它定义了哪些函数
  决定——`fn background` 在角色之后，`fn foreground` 在成片之上。两个都写，就是一整套
  天气写在一个文件里。
- **着色图**只管一个模型上的一个样式组，可用的是该表面自身的数据：贴图、法线、视线
方向。
- **调色预设**最后作用，均匀施加于每一个像素，此时画面已经成型。

三者均**写在场景文档之内**，因此发布出去的场景能原样重现你的风格，与对方是否拥有你用
过的预设无关。

## 2.2 调色预设

调色采用 **ASC CDL**：美国电影摄影师协会的 Color Decision List，影视后期即以此为基
础。三个色调区间，每个区间各有 slope、offset、power，实际操作通过色轮完成。这套术语与
其他调色工具相通，两边可以互相迁移。

### 编辑器

打开调色库，将鼠标停在某个预设上选择 **Edit**；或直接从 **Scene → Grade** 编辑当前应
用的这套。编辑器背后即是预览——每一次调整都实时落在你自己的角色、你自己的光照上。判断
一次调色是否成立，这是唯一可靠的办法。

**Split tone**（−1 到 +1）放在最前面是有意为之：就单个动作而言，它最能表达调色意图，
使暗部与亮部沿冷暖轴向相反方向偏移。负值为冷暗部配暖亮部，即现代电影常见的「青橙」；
正值反之，暖暗部配冷亮部，观感近于烛光、日落或回忆。

**三个色轮**——shadows、midtones、highlights——分别控制三个色调区间：

- **角度**——该区间偏向的色相。
- **离中心的距离**——偏移的程度。
- **色轮旁的滑轨**——该区间的明度。把暗部滑轨往下拉就是压黑，把亮部滑轨往上推就是
提亮。

**Contrast**（0.5 – 1.6）以中灰为轴，**Saturation**（0 – 2）缩放色彩浓度，0 为黑白。

### 工作方法

按此顺序进行，结果最为可控：

1. **先把灯光调对。** 调色是在光给出的底子上做加法。人物显得发平时，应先调整太阳仰角
  与环境光强度，而非急于动调色。
2. **设定 split tone**，然后停一下。很多情况下这一步即是整个调色，其后皆为修饰。
3. **先用滑轨压黑或提亮，再推色相。** 明暗比色彩更显眼，也限定了色彩能走多远。色相一
  次只推一个区间，且应比预想的更克制：色轮推到一半，风格已经相当强烈。
4. **饱和度留到最后**，通常仍是向下压；判断时将强度置为 1，之后再回 Scene 标签设定真
  正需要的强度。在半强度下调色，容易一路调过头。

有两个习惯值得养成。其一，**经常与 Neutral 对比**：看久了什么都会变得正常，切到
Neutral 停两秒，这次调色是否值得保留便一目了然。其二，**按导出分辨率调整**——小窗口中
看着合适的 bloom 阈值，到 4K 可能一触即发光。

### 保存与分享

编辑预设打开的是一张草稿纸。关闭时会问你是否把结果留成一份属于你的**草稿**——保存在
本地浏览器中，可以重命名、继续修改、应用到任意多个场景。一旦成为草稿，之后就是随改随
存，不会再问。草稿是私有的，不会离开你的机器。

调色也可以从编辑器标题栏**导出/导入 JSON**，因此一套调色可以手写、由工具生成，或直接
发给别人，不需要场景，也不需要账号。着色图编辑器上有同样的按钮。

**Publish** 将草稿变为一个署你名字的库条目，所有人可见。这一步的含义见
[§2.5](#25-草稿发布与版本)。

## 2.3 用 WGSL 写场景特效

场景特效是一段着色器，按像素、从视线方向和时钟画出画面的一层。雨、雪、极光、
地面上的雾、缠在身上的闪电、脚下旋转的法阵、片头字卡。

### 六个挂载点

**你定义了哪些函数，就决定了这个特效是什么、画在哪一层。** 应用里没有任何"图层"
设置项，代码本身就是答案。

| 定义 | 得到 |
| --- | --- |
| `fn background(ray, uv, time)` | 背景与角色之间的一层 |
| `fn foreground(ray, uv, time, depth)` | 覆盖在成片之上的一层 |
| `fn particleInit` · `particleStep` · `particleShade` | 一个 GPU 粒子池 |
| `fn trailWidth` · `trailShade` | 沿着你申请的骨骼画的飘带 |
| `fn lightEmit` | 真正参与角色着色的光源 |
| `fn gridStep` | 一张跨帧保留的模拟网格 |

同时定义 `background` 和 `foreground`，它们就是一个特效：一场暴雨是压暗的天空
加上它前面的雨丝，写在同一个文件里。

粒子和飘带各自独立。一个特效要么声明场（`background`/`foreground`）挂载点，
**要么**声明粒子，不能两者兼有——需要自带天空的火花，得写成两个特效依次应用。

### 声明你需要的东西

文件顶部的注释，每行一条。它们是契约的一部分，不是说明文字：

```wgsl
// @anchor 頭              按名字要一根骨骼   -> rzAnchor(subject, 0)
// @anchor 左手首 trail    ……并保留它的轨迹   -> rzTrail(subject, 1, i)
// @particles 4096         粒子池大小，配合粒子挂载点
// @blend additive         粒子叠加发光，而不是覆盖
// @bloom                  粒子进入辉光金字塔
// @fullres                场挂载点按全分辨率运行
// @layer additive         场本身叠加发光，而不是覆盖
// @lights 4               光源槽位数，配合 fn lightEmit
// @grid 768               模拟网格分辨率，配合 fn gridStep
```

**`@layer additive` 是新特效最常需要、也最常漏掉的一条。** 默认按 alpha-over
合成，这对有实体的东西是对的——烟、雾、画出来的天空；对"光"就是错的，而且两道
辉光一交叉就立刻看得出来：后画的那道会遮住先画的，于是第二道闪电在第一道上打了
个洞。十五个内置特效里有七个声明了它。如果你画的是光而不是物质，你也应该声明。

`@anchor` 的槽位就是**声明顺序**——第一条是槽位 0。模型有的骨骼都能用，遇到写法
不同的模型 `.valid` 会是 false。一定要判断，否则你的手部特效会在半数模型上画到
世界原点去。

`@fullres` 开销翻倍，换来亚像素级的细节。发丝般的细线、细环、扫描线需要它；烟、
辉光、翻滚的噪声不需要——双线性上采样本来就能免费带出这些，这正是默认半分辨率的
意义。

### 契约

```wgsl
fn background(ray: vec3f, uv: vec2f, time: f32) -> vec4f
fn foreground(ray: vec3f, uv: vec2f, time: f32, depth: f32) -> vec4f
```

| 参数 | 含义 |
| --- | --- |
| `ray` | 该像素的世界空间视线方向，已归一化。它**随镜头环绕而转**，所以由它算出的东西钉在世界上，而不是钉在屏幕上 |
| `uv` | 屏幕坐标，0 – 1，原点在**左下角** |
| `time` | 特效应用之后经过的秒数 |
| `depth` | **仅 `foreground`。** 场景在这个像素上画的东西有多远（场景单位）；什么都没画的地方是远平面 |

返回值是**带直通 alpha 的 sRGB 颜色**，而 alpha 才是关键的那一半：它是你对身后
一切的遮罩。

- `alpha = 0` —— 透明，背后原样透出。
- `alpha = 1` —— 不透明，你的特效取而代之。

稀疏的特效——雨、火花、脚印——在标记之间把 alpha 压到接近 0，只在落点抬起来。
铺满的特效——渐变天空、绘制的背景——处处返回 1。

### 读取场景

特效不局限于它自己那个像素。这正是"装饰"和"会对表演做出反应的东西"之间的分界。

| 函数 | 给你 |
| --- | --- |
| `rzResolution()` | 画布像素尺寸，用于宽高比校正 |
| `rzCameraPos()` | 相机在世界空间中的位置 |
| `rzCameraRight()` · `rzCameraUp()` · `rzCameraForward()` | 相机的三个轴 |
| `rzSubjectCount()` | 场景里有几个角色，最多四个 |
| `rzSubject(i)` | `{ root, center, bounds, valid }` |
| `rzAnchor(subject, slot)` | 你声明的某根骨骼的 `{ pos, vel, fwd, valid }` |
| `rzTrailCount(subject, slot)` · `rzTrail(subject, slot, i)` | 那根骨骼最近的**轨迹**——`xyz` 是它当时在哪，`w` 是那是多少秒以前 |
| `rzWorldPos(ray, depth)` | 把这个像素的深度变成一个**位置** |
| `rzProject(p)` | 相机眼中的一个世界点——`xy` 是它落在的 uv，`z` 是它沿视轴的距离 |

其中三条值得再读一遍。

**`rzSubject().bounds` 是一个"宽松的"剔除球，不是贴身包围盒。** 它的尺寸要能盖住
举起来的手臂，所以它适合拿来做剔除，不适合拿来定任何东西的尺寸。想知道一个人实际
多大，用胯高——`center.y - root.y`——这在任何骨架上都是身高一个可靠的比例。拿
`bounds.w` 去定地面法阵的大小，会得到一个好几个身高那么宽的圆。

**`rzProject` 是让"锚定在世界上"这件事变得划算的关键。** 在 3D 里推进一条曲线，
每个像素每个采样都要算一次距离；把它的点投影一次、在 2D 里量，只要一次减法。它的
`z` 可以直接和 `depth` 比较，所以遮挡只是一次判断——你的 `z` 更近就画——而且它在
相机背后是负值，用 `uv` 之前值得先排掉。

**飘带是由轨迹做出来的。** 一个位置加一个速度只能给出一段会抖的直线段，因为速度是
两帧之间的差；轨迹才是真正发生过的事。它按**场景时钟**定速采样，所以在编辑器里、
在导出里、在重新导出里都完全一致，间距也不随你的帧率变化。

循环要循环到那些 count 函数，绝不要写死常数。四个角色、八个 anchor、128 个轨迹
采样都是**下限**，它们可以增长——而这一点只有在没人写死数字的前提下才成立。

早期的特效用的是 `bgResolution`、`bgCameraPos`、`bgWorldPos`、`bgSubjectCount`
和 `bgSubjectPos`。这些名字仍然有效，并且会永远有效——发布出去的场景是一条永久
链接，所以它依赖的任何东西都不会被移除。

### 跟着音乐动

| 函数 | 给你 |
| --- | --- |
| `rzAudioLevel()` | 当前响度，0 – 1 |
| `rzAudioOnset()` | 低频**上升**得有多猛——鼓点检测器 |
| `rzAudioBandCount()` · `rzAudioBand(i)` | 频谱，对数分布，每个频段 0 – 1 |
| `rzAudioLevelAt(o)` · `rzAudioOnsetAt(o)` · `rzAudioBandAt(i, o)` | 同上，但偏移 `o` **秒**——负数是过去，正数是未来 |
| `rzAudioTime()` · `rzAudioPlaying()` | 歌放到哪了，以及是否在播 |

整首曲子是**提前一次性分析**好的，不是实时采样。这正是导出能和编辑器完全一致的
原因：导出是一帧一帧步进引擎，而不是实时播放，实时分析器在那种情况下只会听到寂静，
于是所有音频响应特效都会从视频里悄悄消失。

这也是 `At(offset)` 这几个形式存在的理由。未来已经算好了，所以一根柱子可以在鼓点
**落下之前**就开始迎上去——这是实时分析器做不到的。场景没有音乐时，全部读数为零。

### 乐谱与歌词

音轨旁边放一个 `.mid`，特效就能读到音符；放一个 `.lrc`，就能读到此刻该出现的那
一句。两者都跑在与音频同一条预先算好的时钟上，所以导出与编辑器里完全一致。

| 函数 | 给你什么 |
| --- | --- |
| `rzMidiTime()` · `rzMidiDuration()` · `rzMidiPlaying()` | 乐谱走到哪、总长多少、是否在走 |
| `rzNoteCount()` | 文件里有多少个音符 |
| `rzNoteStart(i)` · `rzNoteLength(i)` | 第 `i` 个音符何时开始、持续多久，单位秒 |
| `rzNotePitch(i)` · `rzNoteVelocity(i)` | 它的 MIDI 音高，以及力度 0 – 1 |
| `rzNoteAge(i)` · `rzNoteHeld(i)` | 距它开始过了多少秒；此刻是否还在响 |
| `rzPitchLow()` · `rzPitchHigh()` | 这个文件实际用到的音域——键盘的真实跨度，而不是 0 – 127 |
| `rzPitchX(pitch)` | 把音高映射到音域上的 0 – 1，于是布局不必知道曲子是什么 |
| `rzKeyEnergy(pitch)` | 这个音此刻还剩多少能量（带衰减）——一个仍在余响的琴键 |

音符**按开始时间排好序**，所以用二分查找定位当前窗口，而不是遍历整个文件。
*Note Fall* 就是这么做的，这也是它能承载一整卷钢琴谱的原因。

| 函数 | 给你什么 |
| --- | --- |
| `rzLyricCount()` · `rzLyricIndex(t)` | 一共几句；`t` 时刻是第几句，句与句之间返回 `-1` |
| `rzLyricStart(i)` · `rzLyricEnd(i)` | 这一句的时间窗，单位秒 |
| `rzLyricProgress(i, t)` | 这一句走了多少，0 – 1——卡拉 OK 的扫光 |
| `rzLyricHasText(i)` | 这一句有没有栅格化出内容 |
| `rzLyricText(i, uv)` | 第 `i` 句的字形覆盖率；`uv` 是它自己那个框上的 0 – 1 |
| `rzLyricAspect(i)` · `rzLyricPixels(i)` · `rzLyricRect(i)` | 宽高比、在图集里占多少纹素、位于图集何处 |
| `rzLyricChars(i)` | 这一句有多少个字 |

文字由宿主栅格化，不在着色器里排版——特效采样的是覆盖率。要**按一个像素的宽度去
采**，而不是采一个点：字形边缘是一个阶跃，小字号下采点会随着这一句移动而闪烁。
`rzLyricPixels` 就是把屏幕上的足迹换算成正确滤波宽度的那个量。

场景里没有 `.mid` 或 `.lrc` 时，这里的一切返回 0、`-1` 或 `false`，所以用到它们
的特效在两样都没有的场景里照样能编译、能画。

### `depth` 是用来做什么的

前景并不是被钉在最前面。`depth` 让它可以逐像素地决定。

**拿来比较。** 一颗粒子知道自己有多远。如果场景更近，这个像素归场景——于是同一帧里
雨滴既能从肩膀后面穿过，也能落在脸的前面。比较要做羽化，否则轮廓会呈锯齿：

```wgsl
// 挂在 `dist` 处的一层幕布，在这个像素上还剩多少。
fn curtain(dist: f32, depth: f32) -> f32 {
  return smoothstep(dist - 0.6, dist + 0.6, depth);
}
```

**直接读。** 雾根本不需要比较——它的不透明度本身**就是**距离的函数，所以
`1.0 - exp(-depth * density)` 已经是雾了；场景没画到的像素报告的是远平面，这正是
它会自动把天空盖住的原因。

**把它变成位置。** 凡是属于某个**地点**而不是某个距离的东西，用
`rzWorldPos(ray, depth)` 取到场景画出的那个世界点，镜头环绕时图案就不会跟着漂。

动手之前有一点要清楚：在那个单一深度上求值的前景，是场景所画表面的函数——是那个
表面**上**的一层纹理。它无法知道相机和它**之间**的空气。想要角色是站在里面而不是
站在后面的东西，就自己在 `rzCameraPos()` 和 `rzWorldPos(...)` 之间推进射线、边走
边累加。

### 两种取向

用 `ray` 还是用 `uv`，是第一个决定，它决定了镜头移动时这个特效的行为。

**屏幕空间**，来自 `uv`——粘在画框上。不管镜头看向哪里，雨都顺着屏幕往下落。天气、
暗角、颗粒都该这样。

```wgsl
fn background(ray: vec3f, uv: vec2f, time: f32) -> vec4f {
  // 做宽高比校正，圆才是圆的。
  let res = rzResolution();
  let p = (uv - 0.5) * vec2f(res.x / res.y, 1.0);
  let vignette = smoothstep(0.8, 0.2, length(p));
  return vec4f(vec3f(0.02, 0.03, 0.08), 1.0 - vignette);
}
```

**世界空间**，来自 `ray`——是环境的一部分。镜头绕过去它待在原地，像真的天空一样。
用天空盒采样时同一套映射来投影射线：

```wgsl
fn background(ray: vec3f, uv: vec2f, time: f32) -> vec4f {
  // 经纬度——天空盒自己的投影。
  let sky = vec2f(atan2(ray.x, ray.z), asin(clamp(ray.y, -1.0, 1.0)));
  let band = smoothstep(0.0, 0.35, sky.y);          // 地平线 → 天顶
  return vec4f(mix(vec3f(0.85, 0.45, 0.30), vec3f(0.06, 0.09, 0.22), band), 1.0);
}
```

要有意识地选：用 `uv` 做的星星会在镜头环绕时从天上滑过去，观众哪怕说不出哪里不对，
也会立刻觉得不对。

还有第三种情况很容易踩坑。如果你的特效附着在角色身上，而且它内部有个"向上"的方向
——火焰往上窜、光柱立起来——那么**屏幕的上**不等于**世界的上**。拿画面的 `+y` 来量，
火焰就会跟着镜头倾斜，你从下面绕过去时它会横着窜出画面。应该从角色身上投影一个世界
向上的向量：它在屏幕上的方向才是你要的，而它被透视压缩后的长度，正好就是从这个角度
看过去这个特效该有多高。

### 光源

特效可以把光送进**着色**里，而不只是往画面上糊像素。声明槽位数，然后填满它们：

```wgsl
// @lights 4

fn lightEmit(i: u32, time: f32) -> RzLight {
  var l: RzLight;
  l.pos = vec3f(0.0, 12.0, 0.0);   // 世界坐标
  l.color = vec3f(1.0, 0.85, 0.6);
  l.intensity = 0.0;                // 0 是"关掉"，不是"一盏很暗的灯"
  l.radius = 8.0;                   // 衰减距离
  return l;
}
```

每帧对每个槽位调用一次。数量与函数成对出现——只写其中一个是编译错误，`@lights`
的上限由引擎决定。

`intensity = 0` 会把这个槽位整个撤掉，这正是爆发类特效便宜的原因：烟花在两次绽放
之间不是"一盏亮度为零、还杵在某处的灯"，而是根本没有灯。每次调用都要把每个字段都
写一遍——你不管的字段会留着上一帧的值。

这是**唯一**会改变角色本身长相的挂载点。辉光不会：它在着色之后于屏幕空间扩散亮
像素，所以一条发光的飘带并不会照亮它旁边的裙子。光源会。

### 粒子

三个函数，而且整个粒子池从不经过 CPU：一次 compute dispatch 推进所有粒子，一次
实例化绘制把它们画上屏幕。

```wgsl
// @particles 4096
fn particleInit(i: u32, seed: f32) -> Particle    // 一颗新粒子
fn particleStep(p: Particle, dt: f32) -> Particle // 一帧的运动
fn particleShade(p: Particle, uv: vec2f) -> vec4f // 它的公告板，uv 0–1
```

`Particle` 带有 `pos`、`vel`、`age`、`life`、`size`、`rot`、`seed` 和 `stretch`。
在 `particleStep` 里把 `life` 置零就是让它退休，它会带着新的种子从 `particleInit`
回来。`stretch` 是沿运动方向的长宽比：1 是方形公告板，一滴雨是 10 或 20。

粒子是在**场景 pass 内部**绘制的，所以它们免费享有对角色的深度测试——在肩膀后面的
一颗火花直接就被挡住了，你什么都不用做。*Snow* 和 *Rain* 是范例。

### 飘带

两个函数，作用在每一根用 `trail` 声明过的骨骼的记录轨迹上：

```wgsl
// @anchor 右手首 trail
fn trailWidth(u: f32, age: f32) -> f32                                  // 像素
fn trailShade(u: f32, v: f32, age: f32, weight: f32, slot: i32) -> vec4f
```

`u` 沿飘带走，`v` 横跨飘带，所以柔边是 `v` 的函数、收尖是 `u` 的函数。轨迹会被平滑
成样条并在**屏幕空间**挤出，因此不管镜头怎么动，飘带都保持自己的宽度。

飘带在自己的图层里用 MAX 混合、在色调映射之后合成。这正是一条明亮的飘带自我交叉时
不会叠成一团白的原因。*Hand Ribbon* 是范例。

### 模拟网格

这里其他所有东西都是无状态的——同样的 `time` 给出同样的一帧。网格是例外：一张归
特效自己所有的纹理，每帧步进一次，每一帧读上一帧。

```wgsl
// @grid 768

fn gridStep(uv: vec2f, prev: vec4f, dt: f32) -> vec4f {
  if (rzGridFrame() == 0) { return vec4f(0.0); }   // 第 0 帧是你的初值
  let te = rzGridTexel();                          // 一个纹素，折算成 uv
  let left = rzGridPrev(uv - vec2f(te, 0.0));      // 上一帧的任意一格
  return prev;                                     // 四个浮点，含义由你定
}
```

四个通道装什么由你决定。*Dry Ice* 把速度放在 `xy`、密度放在 `z`、压力放在 `w`，
这已经够跑一个真正的流体了：投影、逆向平流、注入、衰减。场挂载点再用 `rzGrid(uv)`
读这张稳定下来的网格并着色——在那个特效里，是把它当作地面上方的体积去 march。

| 函数 | 给你什么 |
| --- | --- |
| `rzGrid(uv)` | 这一帧的格子 |
| `rzGridPrev(uv)` | 上一帧的——`gridStep` 读的就是它 |
| `rzGridTexel()` · `rzGridSize()` | 一个纹素折算成 uv，以及分辨率 |
| `rzGridFrame()` | 特效应用以来的帧数；`0` 是该写初值的那一帧 |

分辨率和别的开销一样是要花钱的：768² 是每帧步进五十多万个格子。默认 256，上限由引
擎卡住。`dt` 是真实经过的时间，所以用它积分出来的东西在帧率变化时依然成立——但模拟
是一段历史，从场景中途开始的导出，拿到的是一张空网格，而不是你刚才看到的那一张。

### 让它跑得快

这段代码要在一整个角色渲染之后、每一帧、最高 4K 分辨率下运行，而导出会把它乘以
几千帧。两个习惯就能解决绝大部分问题。

**先剔除，而且要分层剔除。** 如果你的特效属于某个角色，那就在做任何逐标记的准备
工作之前，先把离她很远的像素排掉——任何一帧的大部分都是空的。然后在逐**标记**准备
之前先逐**肢体**剔除：一个在手臂旁边的像素，可以用一次比较就丢掉另一条手臂和两条腿
上的所有东西，这比把每个标记本身做便宜要值钱得多。

**剔除半径要推导出来，绝不要猜。** 猜出来的半径会把你自己的特效切掉，而且它出问题
的样子根本不像半径：圆的顶部附近，边界在很宽一段里平直到一个像素以内，所以一个偏小
的包围盒看起来就像有人在你的作品上画了一条直线。把半径写成那些真正会伸出去的量之和
——一个标记能离锚点多远，加上它自己会扩散多远——这样你调参数时它会跟着变。

**每一处辉光都要有界。** `1/r` 的衰减永远到不了零，也就给不了你任何可以用来剔除的
半径；有界的衰减给得了，而且没人分得出两者的区别。

把特效设为 *None* 单独导出一次，就能知道帧时间里有多少是你的。

### 编辑循环

打开 **场景 → 特效 → 库**，点 **新建特效** 得到一份带注释的起始模板，或者右键任何
预设、选 **编辑着色器** 来 fork 它。

**<kbd>⌘/Ctrl</kbd>+<kbd>Enter</kbd> 编译并应用。** 场景就是预览——没有单独的渲染
按钮。成功后特效立刻生效。失败时上一个着色器保持应用，你会拿到 `line:column` 位置
已经重新映射到你自己代码上的诊断信息，所以迭代过程中永远不会只剩一块黑屏。

### 规则

- **自包含。** 没有贴图、没有外部绑定、帧与帧之间没有状态。
- **所有运动都由 `time` 驱动。** 它是唯一的时钟，也是导出视频可复现的原因。
- **循环要定长且小**，共用的计算要提到循环外面。
- **`fwidth` 只能用在一致控制流里。** 只要相邻像素走了同一条分支，导数就是成立的
  ——别把它放在依赖数据的提前返回之后。
- **WGSL 不区分声明顺序**，所以辅助函数可以写在用到它们的函数下面。

另外五条是踩出来的，每一条都换来过一轮"看着不对，但说不清哪里不对"：

- **体积要 march 光线，而不是给深度缓冲上的那个点着色。** 在深度缓冲报告的世界
  坐标处采样密度，结果只可能是"地板在哪里"的函数——一张画在地上的贴图。它表达不了
  角色**前面**的空气，所以永远也裹不住一个人。
- **march 的范围要解析地卡住。** 先把光线和体积自己的形状求交。采样不足会表现为
  颗粒感；而步长在"打到地面"和"射向天空"之间突变，会表现为一道地平线形状的裂缝。
- **每一个 `1/r` 辉光都需要一个有限的边界。** `size / (d + ε)` 永远到不了零，于是
  裁剪会切掉仍然有效的信号，辉光再把这道切口变成一个环。让它在裁剪半径处**恰好衰
  减到零**——`smoothstep(REACH, 0.0, d)`——边界才是一个定义，而不是一个估计。
- **裁剪半径要从可见度下限推出来，并且记得色调映射会把它抬高。** alpha 按
  `1 − exp(−1.52·c)` 解算，所以一个值远在自身大小的 1/255 以下时仍然可见。拿原始
  值去估半径，会切进画面里。
- **亮度就是不透明度。** 一层的 alpha 就是它自己的能量，所以暗的光带同时也是透的，
  而 `1/r` 辉光会随着调亮而变粗。把宽度和亮度做成两个独立的旋钮，否则唯一看得清的
  光带就只有粗的那种。

每个预设都是一个范例，注释里写着它是为了避开哪个坑而这么写的。读它们是进入这套写法
最快的路。

## 2.4 材质着色图

着色图规定一个样式组的表面怎么响应光照。它是 Blender 那种节点图：带类型的插槽，用连线
接起来，编译成 WGSL，实时生效。

从 Materials 标签点开某组的着色图名称，**Browse all…**，再对任意一条选 **Edit
graph**。内置图分两套，外加一个中性底子，都是可以直接 fork 的参考实现：

- **AG**——*AG Body*、*AG Eye*、*AG Face*、*AG Hair*、*AG Metal*、*AG Rough
  Cloth*、*AG Smooth Cloth*、*AG Stockings*。八个各类表面的现成例子，都是围绕一个
  光照闭包加一条渐变搭起来的。
- **WuWa**——*WuWa Body*、*WuWa Cloth*、*WuWa Hair*、*WuWa Face*、*WuWa Metal*、
  *WuWa Eye*。每张二十一个节点，不走闭包而是直接用光：半兰伯特穿过一段很窄的软阈值，
  阴影在转向受光的途中经过一段暖色，再叠上模型自带的球面贴图高光与边缘光。想要硬
  转折的二次元观感就从这里起步。
中性底子不在库里：未分组材质本来就是它，新建组和新建图也都从它开始，把它摆进货架
等于给空白页做一份副本。

两套都不自带任何贴图。预设读的是材质本身的贴图与球面贴图，因此可以用在任何模型
上——你自己发布预设时，这一点值得保持。

### 节点面板


| 分类             | 内容                                                            |
| -------------- | ------------------------------------------------------------- |
| **Input**      | 表面自身的数据：贴图采样、几何（法线、视线方向、世界坐标与静止坐标、UV、反射）、材质自带的漫反射色与球面贴图、数值与 RGB 常量 |
| **Scene**      | `light`——主光源的方向、颜色、环境光、阴影；`head_basis`——头部骨骼的前/右/上轴          |
| **Colour**     | 色相/饱和度、亮度/对比度、反相、gamma、RGB 曲线、RGB/HSV/HSL 的分离与合并，以及颜色渐变——线性、常数、cardinal、抗锯齿常数、三角，以及三色标线性 |
| **Texture**    | 程序化噪声、渐变与 voronoi，另有样式组自带的至多四张图像贴图                            |
| **Vector**     | 映射、bump、法线贴图、分离/合并 XYZ、矢量旋转、矢量变换，以及 24 种矢量运算                  |
| **Math / Mix** | 39 种算术运算、20 种混合模式、映射范围                                        |
| **Shader**     | Principled BSDF、自发光、add/mix shader、shader-to-RGB（颜色或标量）、漫反射与透明 BSDF、菲涅尔、layer weight |


最常打交道的插槽名是 `color`、`alpha`、`normal`、`view`、`uv`、`fac`（0–1 混合因子）、
`strength`、`roughness`、`metallic` 和 `base_color`。

**直接取用光源。**`shader_to_rgb_diffuse` 与 `bsdf_diffuse` 会把整个光照闭包算完再
把结果交给你，这是 AG 那一套的写法。而 `light` 节点把太阳光以数值形式暴露出来，让图
自己构造光照项——`dot(normal, direction)` 再送进渐变或阈值——这正是二次元着色硬转折
的来源，也是 WuWa 那一套的基础。

### 搭建

- **添加节点**：在画布上右键，或使用添加菜单，可按名称搜索。
- **连线**：从输出插槽拖至输入插槽，类型须匹配。
- **未连线的输入使用其默认值**，直接在节点上修改即可。一条连线都没有的图同样合法。
- **指定输出**：右键节点选择 *Set as output*。这即是材质真正渲染的值，每张图有且只有一个，且必须是颜色（`vec3f`）或标量（`float`）。
- **预览任意插槽**：*Preview output* 将某个插槽直接送至屏幕，单独查看这一支算出了什么；*Stop preview* 回到真正的输出。这是编辑器中最有效的排查手段——图看着不对时，从输出向回逐个预览，第一个异常之处即是问题所在。
- **Generated WGSL**：编辑器会显示这张图编译出的代码，结果与预期不符时值得一读。

节点的位置只是排版。移动节点不影响结果，重新排版过的图，仍视作与其来源的库条目完全一致。

### 图即文档

编辑器搭出的一切都是一份纯 JSON 文档——reze-engine 的 `ShaderGraph`——直接书写文档
同样是一等的创作方式。完整结构如下：

```jsonc
{
  "version": 1,
  "name": "My Graph",
  "nodes": [
    // id：唯一，/^[a-z0-9_]+$/ · type：下表中的注册 id
    // inputs：未连线插槽的字面默认值
    { "id": "tex", "type": "texture" },
    { "id": "diff", "type": "material_diffuse" },
    { "id": "base", "type": "mix/multiply", "inputs": { "fac": 1.0 } },
    { "id": "shade", "type": "shader_to_rgb_diffuse" },
    { "id": "band", "type": "ramp_constant_aa",
      "inputs": { "edge": 0.35, "color0": [0.62, 0.58, 0.72, 1], "color1": [1, 1, 1, 1] } },
    { "id": "lit", "type": "mix/multiply", "inputs": { "fac": 1.0 } }
  ],
  "links": [
    { "from": { "node": "tex",   "socket": "color" }, "to": { "node": "base", "socket": "a" } },
    { "from": { "node": "diff",  "socket": "color" }, "to": { "node": "base", "socket": "b" } },
    { "from": { "node": "shade", "socket": "value" }, "to": { "node": "band", "socket": "fac" } },
    { "from": { "node": "base",  "socket": "color" }, "to": { "node": "lit",  "socket": "a" } },
    { "from": { "node": "band",  "socket": "color" }, "to": { "node": "lit",  "socket": "b" } }
  ],
  "output": { "node": "lit", "socket": "color" }
}
```

这个例子本身就是一个可用的赛璐璐着色器：贴图乘以材质自带的漫反射色，再把量化成
两段的漫反射光照乘上去。`output` 必须解析为颜色（`vec3f`）或标量（`f32`）；合理
处会自动转换。可选的
`params` 数组把选定的节点输入暴露为命名滑杆，调整即时生效、无需重编译；`tags`
是库检索用的自由标签。

| --- | --- |

### 写出能编译的图

编辑器在拖拽时就把你限制在 schema 之内：只给出真实存在的插槽，连不上的目标会变暗，
第二条线落到已被占用的输入上会替换掉原来那条。手写或由工具生成的文档没有这层保护，
因此要在进入画布之前先检查——编辑器标题栏的 **Import graph JSON** 会先校验文件，
把问题列在诊断面板里。以下是写出一份一次过关的文档所需要的东西。

**大多数图共用同一副骨架**，从它起步，一个表面就已经完成大半：

1. **基础色**——`texture` 乘以 `material_diffuse`，即一个 `fac: 1` 的
   `mix/multiply`。少了这一乘，无贴图的材质会渲染成白色。
2. **光照项**——`shader_to_rgb_diffuse` 接入一条渐变：赛璐璐色阶用
   `ramp_constant_aa`，柔和过渡用 `ramp_linear`。若这个表面该是有光照的 PBR 而非
   toon，就用 `principled` 顶替这一步。
3. **两者相乘**——再来一个 `fac: 1` 的 `mix/multiply`，把渐变乘到基础色上。仅此
   已是一个可用的赛璐璐着色器。
4. **然后再加**——`fresnel` 或 `layer_weight/facing` 接 `emission`，用
   `add_shader` 叠上去，得到轮廓光；`mix/add_emit` 用于发光区域；`bump` 或
   `tex_noise` 接进 `principled.normal` 增加表面细节。

把日后想重新调的那两三个数值暴露成 `params`，它们就成了实时生效、无需重编译的滑杆。

结果依据的规则如下。

**结构。** `version` 为 `1`。节点 id 唯一，且符合 `/^[a-z0-9_]+$/`——小写字母、
数字、下划线，别的都不行；`type` 是上表中一字不差的注册 id：`math/power`，不是
`Math`，也不是 `power`。每个输入插槽最多一条连线，整张图无环，`output` 必须解析为
颜色或浮点——`vec4` 输出会被拒绝，浮点则自动铺开成颜色。单张图上限 64 个节点、16
个暴露参数。

**字面值与连线。** `inputs` 为未连线的插槽提供字面值，形状必须与插槽相符：三分量
向量放在 `float` 插槽上是错误，而标量会铺开到颜色、向量和 `vec4` 插槽。承载「被处理
的那个值」的插槽——`invert.color`、`separate_xyz.vector`、`principled.base`、各类
渐变的 `fac`——要么连线，要么显式写出字面值；把它留在注册表默认值上才是错误，并且
只对真正参与输出的节点报告。渐变的两个色标（`color0`、`color1`）是 `vec4`，只能是
字面值，任何连线都进不去。

**参数**只能指向未连线的输入，一个插槽至多一个参数，且 `kind` 必须与插槽类型一致。
由于 `kind` 只有 `float` 和 `color`，色标根本无法暴露——想让 toon 的暗部色可调，
就让它经过一个 `mix/*` 节点，暴露该节点的颜色输入。参数指向的节点若被剪掉，图照样
编译，只是会警告这个滑杆不起作用。

**类型会隐式转换**，因此从不需要转换节点：颜色 → 浮点取 BT.601 亮度，浮点 → 颜色或
向量做铺开，颜色与向量互相直通、比特不变。向量 → 浮点会被拒绝，与 Blender 完全
一致——请用 `separate_xyz`。

**坐标系是引擎的**：左手、Y 轴向上，即 PMX 的约定，而 Blender 是右手、Z 轴向上。
法线的竖直分量是 `separate_xyz` 的 `y` 而非 `z`；照 Blender 写下的方向向量
`(x, y, z)`，在这里是 `(x, z, y)`，符号还需再确认一遍。UV 不变。这一处弄错，画面
看着像那么回事，但光是从错误的轴打过来的——手写图最常见的错误正是它。

**这套词汇里有的东西**——它比 Blender 用户预想的要宽，先知道形状，省得去重建
已经存在的东西：

- **39 种数学运算**与 **24 种矢量运算**——就是 Blender 的完整集合，连保护措施一起：
  除以零得 0 而非无穷，取模是截断式的，各通道混合模式的钳制方式也与 Blender 一致。
- **20 种混合模式**——Blender 的全部类型，含 screen、dodge、burn、soft light、
  difference、色相、饱和度、颜色、明度，外加 `mix/add_emit`。
- **渐变**：四种插值的双色标、一个**三色标线性渐变**（`ramp_linear_3`），以及
  `ramp_tri` 覆盖黑→白→黑。三个色标才能让阴影在转向受光的途中经过一段颜色，而
  toon 的暗部之所以是暖的而非灰的，多半就来自这一段。
- **RGB 曲线**：一条曲线的五个采样点，作用于全部通道。
- **样式组图像贴图**——`tex_image/0` 到 `tex_image/3`，由样式组携带的四张额外贴图，
  默认在网格 UV 上取样，也可以喂任意向量给它。

**这套词汇里仍然没有的东西**：

- **节点图不携带贴图。** 内置图一张都不带；带了的预设就只是某一个角色的预设，而不是
  一种风格。请优先使用材质自身的贴图与球面贴图。
- **插槽属于节点，不属于运算。** 无论选中哪种运算，数学节点都有三个数值输入、矢量
  节点都有三个矢量和一个 scale——用不到的那些是惰性的，与 Blender 一致，因此转写时
  逐插槽对应即可。
- **着色的结果就是颜色。** `add_shader` 编译成 `a + b`，`mix_shader` 编译成
  `mix(a, b, fac)`，都作用在 `vec3f` 上——先把每一支求值成颜色，再合起来。
- **色标不能做成滑杆。** 色标颜色是 `vec4` 字面值，而参数只有 `float` 和 `color`；
  想让暗部色可调，就让它经过一个 `mix/*` 节点，暴露该节点的颜色输入。
- **没有 EEVEE Next 的光照。** 没有屏幕空间 GI、没有虚拟阴影贴图、没有辐照度探针。
  Principled 中的 coat、透射、次表面、各向异性与薄膜是缺席，而非近似。
- **一张图上限 64 个节点**、16 个暴露参数。

**在编辑器之外检查。** reze-engine 导出 `validateGraph(graph)`，返回上述诊断；
`compileGraph(graph)` 返回 `{ ok, wgsl, diagnostics }`。两者都以诊断报告问题，而
不抛异常。必须连线的插槽、环、被剪掉的节点由编译而非校验报告，因此把图交出去之前
先编译一次。

### 从 Blender 迁移

节点语义跟随 **Blender 5.2**，因此一份材质大多能逐插槽搬过来——Principled 带的就是
v2 的插槽名（`base_color`、`specular_ior_level`、`sheen_weight`），数学、矢量与混合
的运算集合也是 Blender 自己的，连同保护措施一起从它的 GLSL 转写而来。reze 不读
`.blend` 文件：转换是创作阶段做一次的翻译。

仍有两处不同，改变的是数值而非结构。**这里没有 EEVEE Next 的光照**——没有屏幕空间
GI、没有虚拟阴影贴图、没有探针——因此照探针反弹调好的预设会显得平一些，需要凭眼睛
重调。以及**视图变换由你决定**：Post 行的 Tone 里有 Standard 与 Filmic，一份在
Standard 下渲染的 `.blend`，在你把它对上之前是不会一致的。二次元与 NPR 通常用
Standard——图算出什么颜色，落到屏幕上就是什么颜色。

**两种写法都能搬过来。** 基于漫反射闭包的材质——Shader to RGB 接一条渐变——直接对应
`shader_to_rgb` / `shader_to_rgb_diffuse`。而自己从光线向量构造光照项的材质（大多数
游戏 NPR 预设都是这么写的）对应 `light` 节点：原图从哪个灯光空物体经驱动器或属性读到
方向，这里就读 `light.direction`，其余链路原样搬运。

**一定要接上场景的光。** 只用 `light.direction` 构造出来的项，材质会完全无视太阳的
颜色与强度、世界环境色以及投影——在场景里换任何一套灯光,画面都不会变。按引擎自己的
式子接回去即可：`light.color × (band × light.shadow ÷ π) + light.ambient`，也就是把
`shader_to_rgb_lit` 里平滑的 N·L 换成你那段硬阈值。但这一项不能整个拿来乘：那样每个
表面都会把世界光的色相乘进去，遇上饱和度高的世界色，整个角色会被拽向那个颜色、暗部
则塌成环境光本身。先把它向白色混一半再相乘，四项（太阳颜色、太阳强度、世界色、投影）
就都还在，而世界色不会独占画面。把 `light.shadow` 先乘进 band 再送进渐变，投影就会
带上与明暗交界线同一种颜色。

**搬不过来的**是图里读取的、模型本身并不携带的贴图：高光贴图、ID 遮罩、面部 SDF。
那些属于某一个角色。原图用 ID 遮罩告诉着色器当前在着色哪个区域时，请改用样式组——那是
同一份信息，内置图也正是这么做的。

**节点对照：**

| Blender 节点 | reze type |
| --- | --- |
| Principled BSDF | `principled`——v2 插槽，见下 |
| Emission | `emission` |
| Mix Shader、Add Shader | `mix_shader`、`add_shader`——按 RGB 运算，见下 |
| Shader to RGB | `shader_to_rgb_diffuse` |
| Image Texture | `texture`——材质自身的漫反射贴图，在网格 UV 上取样 |
| Texture Coordinate、Geometry | `geometry` |
| Value、RGB | `value`、`rgb` |
| Hue/Saturation、Bright/Contrast、Invert | `hue_sat`、`bright_contrast`、`invert` |
| Color Ramp | 按插值方式取 `ramp_constant`、`ramp_linear`、`ramp_cardinal` |
| Math | `math/add`、`math/multiply`、`math/power`、`math/greater_than` |
| Mix Color | `mix/blend`、`mix/overlay`、`mix/multiply`、`mix/lighten`、`mix/linear_light` |
| Fresnel、Layer Weight | `fresnel`、`layer_weight/fresnel`、`layer_weight/facing` |
| Separate XYZ、Vector Math（叉乘）、Mapping、Bump | `separate_xyz`、`vect_cross`、`mapping`、`bump` |
| Noise、Gradient、Voronoi Texture | `tex_noise`、`tex_gradient`、`tex_voronoi/f1`、`tex_voronoi/color` |

节点的模式属于类型字符串的一部分，因为它是拓扑而非参数：`Math` 选 POWER 就是
`math/power`，Color Ramp 的插值方式决定用三种 `ramp_*` 中的哪一个，Layer Weight
选用的输出决定是 `layer_weight/fresnel` 还是 `layer_weight/facing`。有几个类型在
Blender 里没有来源，值得主动用起来——`material_diffuse`（PMX 材质自带的色调；把漫
反射贴图乘上它，否则无贴图的材质会渲染成白色）、`ramp_constant_aa`、`ramp_tri`、
`mix/add_emit` 和 `math/clamp01`。

**Principled BSDF 用的是 v2 插槽**，因此 4.x / 5.x 的材质按名字就能对应。

| reze 插槽 | Blender 5.2 | 说明 |
| --- | --- | --- |
| `base_color` | Base Color | 直接对应 |
| `metallic` | Metallic | 直接对应；v2 的 F82 染色会丢失 |
| `roughness` | Roughness | 直接对应 |
| `ior` | IOR | 与 `specular_ior_level` 一起给出 f0 |
| `specular_ior_level` | Specular IOR Level | 0–1，默认 0.5 |
| `sheen_weight` | Sheen Weight | 直接对应 |
| `sheen_tint` | Sheen Tint（颜色） | 取其亮度 |
| `emission_color`、`emission_strength` | Emission | 与 4.x+ 一样并进 Principled |
| `normal` | Normal | 按上文换轴；不连线即为着色法线 |
| `spec_clamp` | — | reze 独有，相当于 EEVEE 的 Light Clamp；除非带噪声的 bump 打出高光噪点，否则保持关闭 |

`ior` 取 1.5 时，v2 这条链对旧约定是恒等的，因此 3.6 材质的 Specular 数值可以原样
搬过来。其余的要么在创作阶段烘进 `base_color`，要么舍弃：coat、次表面、透射、alpha、
各向异性、切线、薄膜、漫反射粗糙度。

**混合 BSDF 的树是重写，不是誊写。** 先混合闭包、再统一求值的那种结构，必须改写成
Shader-to-RGB 的写法——每一支各自求值成颜色，然后合并——改完的结果需要对着参考渲染
逐一核对。内置图中 *Hair* 是这一写法的范本。

**大树装不下。** 上限是 64 个节点，因此一份 87 个节点的材质必须减掉 23 个。多出来
的部分大多是 reroute、frame 和常量管线，本来就没有运行时意义：把常量子树折叠掉，
把一串字面运算收成单个值，再砍掉那些通往这里并不存在的 Principled 输入的分支。
节点组要先展平，Float 与 RGB Curves 重采样成渐变或一串数学节点，Menu Switch 定到
你要的那一支。Normal Map、Displacement、Attribute、Object Info、Light Path、AOV
Output 则完全没有对应物。

**把没搬过来的东西讲清楚。** 一份被悄悄降级的材质，在接手的人看来就是渲染器的
bug。指明舍弃了哪个 Blender 节点或插槽，以及它是被烘进了别的值、做了近似，还是直接
省略；若原图依赖多色标渐变、变换后的贴图取样或真正的闭包混合，一开始就说明这是重写
而非移植。

### MMD 的惯例

这个生态中的模型自带一些约定，顺应它们要比与之相抗省力得多：

- **Toon ramp。** MMD 模型本身即带有把光照切分成色阶的 toon 贴图。那种标志性的赛璐璐观感，来自一条由法线与光线点积驱动的**常数**或**抗锯齿常数**渐变——两三个色阶，而非平滑过渡。优先使用抗锯齿的那一种，运动时更稳定。
- **轮廓光用菲涅尔实现。** 菲涅尔接入自发光，再叠加到主着色上，即可得到那种「动画打光」的边缘分离感。强度宜小，轮廓光点到为止。
- **眼睛需要单独一张图。** 它比皮肤更平、更饱和，对场景光也更不敏感——*Eye* 单独存在、眼睛样式组自动建立，皆出于此。
- **头发需要各向异性。** 沿头发的静止坐标拉出一条渐变去驱动高光，即可得到这种风格应有的带状光泽。头发上均匀的镜面反射看起来像塑料。
- **丝袜这类多层半透明材质**需借助 alpha hashing 才能正确排序。内置的 *Stockings* 图及其组角色已处理妥当，自行制作时从它起步。

修改时一次只动一处，每改一次回视口确认——结果出乎意料，多半能追溯到三步之前的某条连线。近景与远景都要查看：特写下调好的图，拉远可能变成一片噪点。还需记住开销是相乘的——一张图会在其所属组的每个材质、每个像素、每一帧上运行一遍，因此同一张图用在占满画面的服装上，代价远高于用在眼睛上。

## 2.5 草稿、发布与版本

三处创作位置共用同一套流程，规则只有一条：**留下的东西都在「本地」，没留下的就没有了。**

**你自己的草稿是随改随存的。**每一次改动都会即时写入本地存储，所以关闭草稿就只是关闭——不用确认，误刷新也不会丢。

**其他内容都是草稿纸。**内置预设、别人发布的条目，或是你直接在某个样式组上调出来的效果：编辑时屏幕上是实时生效的，但在你关闭之前不会写入任何地方。关闭时会问你是否留下。留下就进入**本地**，可以重命名、继续改、用到别的场景、发布出去；不留就丢弃——包括你刚才预览它的那个场景，也会回到原样。

正因如此，不存在「存在场景里但不在库里」这种需要另外理解的中间状态：你想要的效果要么在「本地」，要么就不存在。

**草稿应用到场景是按值嵌入的**——场景中携带的是调色、着色器、着色图的实体，因此发布出去的场景才能在他人机器上原样重现。

**发布**会生成一个署你名字的库条目，所有人可见。由此有两条性质：

- **版本不可变。** 在自己的条目上再次发布，写入的是版本 *n+1*，不会覆盖版本 *n*。仍在使用旧版本的场景照常使用它，一字不差。
- **场景锁定具体版本。** 场景记录的是 `{ id, version }`。你下个月把这套预设重调一遍，也不会影响别人上个月用它发布的场景。

因此发布是一种承诺。条目该改就改——版本机制正是为此准备的——而已经发布出去的那些版本，会继续服务于仍在使用它们的人。

未经修改的内置内容走的是另一条路：场景只记录一个裸引用，由应用自身解析。因此一个仅使用内置预设的场景，在断网、无数据库的情况下照样可以渲染。

# 附录 B. 去哪里找模型、动作和音乐

- **BOOTH**（`booth.pm`）——pixiv 的创作市集，目前仍在更新的模型基本都在这里。用日语搜索（`MMD モデル`）结果最全。
- **ニコニ立体**（`3d.nicovideo.jp`）——Niconico 的模型站，Crypton 的官方模型亦在其中。
- **BowlRoll**（`bowlroll.net`）——文件托管站。大量动作与其他资源经由它分发，链接通常挂在 Niconico 视频或推文之下，有时还需输入该帖给出的密码。
- **Aplaybox**（`aplaybox.com`）——大型中文模型站，B 站 MMD 与虚拟主播圈使用广泛。
- **DeviantArt**——欧美圈的老牌阵地，至今仍有大量下载链接。其中不少是他人模型的二次转载，请尽量回到原作者页面下载。

身体动作与镜头动作通常由编舞者按曲目一并放出；搜索歌名加 `モーション配布` 即可找到。动作按标准骨骼编写，可驱动任何模型——比例不符时会出现脚下打滑，换用身材更接近原作者所用模型的角色即可。

音乐需要格外注意：多数舞蹈动作都是为某一首特定的商业曲目编排的。VOCALOID 制作人往往允许非商业的二次创作，DOVA-SYNDROME（`dova-s.jp`）这类免版税曲库把授权写得很清楚，自己制作的当然归自己。发布时音频会一并上传，因此音乐是整个场景中权利风险最高的一项。

# 附录 C. 术语表

**ASC CDL**——美国电影摄影师协会 Color Decision List，Reze Design 调色背后的
slope/offset/power 颜色变换。

**借物表**——列出作品中用到的每一个模型、动作、特效与曲目及其作者的清单。发布时必填。

**骨骼（Bone）**——模型骨架上的关节。动作文件按名称寻址骨骼，这正是文件可互换的原因。

**赛璐璐着色 / toon shading**——把光照量化成平坦色阶而非平滑渐变，MMD 的标志性观感。

**等距柱状（Equirectangular）**——2:1 的全景投影方式，用于 skybox。

**调色（Grade）**——作用于整幅成品画面的颜色变换。

**MME（MikuMikuEffect）**——桌面版 MMD 的 DirectX 9 HLSL 特效插件。这里的对应物是背景
特效和着色图，用 WGSL 编写。

**变形（Morph）**——具名的形变目标，多为表情，由动作文件与骨骼一同驱动。

**PMX / PMD**——MMD 的模型格式，PMX 是现行标准。

**物理**——模型中定义、运行时模拟的头发、布料与挂件运动。

**着色图（Shader graph）**——定义表面如何响应光照的节点图，编译为 WGSL。

**样式组（Style group）**——共用同一张着色图的一组材质。

**利用規約**——模型的使用条款。发布前请阅读。

**VMD**——Vocaloid Motion Data，可能是身体动作，也可能是镜头动作。

**WebGPU**——本应用所基于的浏览器 GPU 接口。

**WGSL**——WebGPU 着色语言。背景特效用它编写，着色图编译为它。
